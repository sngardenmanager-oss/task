# 메인·하위 일정 및 업무 연결

2026-09-27 커밋 `5712a69` 기준. 기획서 "스누피가든 업무프로그램 – 연결 일정 · 연결 업무 기획서"와 그 결정 사항을 구현했다.

## 목적

할로윈 행사처럼 여러 업무가 모여 하나의 결과를 만드는 일을 한 화면에서 관리한다.

- 메인 일정(D-day) 아래 하위 일정을 달고, 하위 일정 날짜를 D-day 기준으로 자동 계산한다.
- 하위 일정을 체크하며 진행률(%)과 지연 건수를 확인한다.
- 진행 중에 생긴 업무를 기존 업무에 "먼저 할 일 / 다음에 할 일 / 관련 업무"로 연결한다.

새 테이블이나 새 탭 없이 기존 `Task`에 선택 필드 3개(`parentId`, `offsetDays`, `links`)를 더했다. 모두 없어도 되는 필드라 기존 업무 데이터는 그대로 동작하고, `workspace_state` JSONB에 함께 저장되므로 DB 마이그레이션도 없다.

## 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 하위 일정 체크 | 팀원이 체크하면 `완료 요청`, 관리자가 승인해야 `최종 완료` |
| 하위가 남은 메인 완료, 선행 미완료 상태의 진행 시작 | 막지 않고 확인창으로 경고만 한다 |
| 기본 템플릿 | 두지 않는다. 사용자가 메인 일정에서 직접 저장해 만든다 |
| 메인 일정의 유형 | 별도 유형을 만들지 않는다. 어떤 업무든 하위 일정을 달면 메인 일정이 된다 |
| 연결 범위 | 모든 업무가 서로 연결될 수 있지만, 연결 없는 업무도 그대로 쓴다 |

## 사용자 매뉴얼

### 메인 일정과 하위 일정 만들기

1. 평소처럼 업무를 만든다. 이 업무의 시작일이 D-day다.
2. 업무 상세의 `하위 일정` 섹션에서 `+ 하위 일정`을 누른다.
3. 업무명을 쓰고 날짜를 `D-day ○일 전/후`로 입력한다. 시작일은 자동으로 계산되어 잠긴다.
4. 날짜를 직접 정하려면 `날짜 직접 지정`을 고른다. 이 일정은 행사일이 바뀌어도 옮겨지지 않는다.

새 업무 입력창의 `메인 일정` 칸에서 기존 업무를 골라도 같은 방식으로 하위 일정이 된다. `+ 하위 일정`으로 열면 분류는 메인 일정의 분류가 기본값이다.

### 진행 확인

- 메인 일정 상세와 업무 카드에 `하위 2/7 · 29%` 진행 막대가 보인다.
- 날짜가 지났는데 완료되지 않은 하위 일정은 빨간색으로, 메인에는 `지연 N건`으로 표시된다.
- 하위 일정 목록의 체크박스: 팀원이 체크하면 `완료 요청`(노란 체크), 관리자가 체크하면 `최종 완료`가 된다. 진행률에는 최종 완료만 들어간다.
- 하위 일정 상세 위쪽의 `↑ 메인명 · D-40` 버튼으로 메인 일정으로 돌아간다.

### 행사일 변경

메인 일정의 시작일을 바꾸면 "D-day 기준 하위 일정 N건도 같이 옮길까요?"를 묻는다.

- `확인`: D-day 기준 하위 일정이 같은 일수만큼 이동한다.
- `취소`: 날짜는 그대로 두고 D-day 기준 일수만 새 D-day에 맞춰 다시 계산한다.
- 완료된 일정과 날짜를 직접 지정한 일정은 어느 쪽이든 옮기지 않는다.

### 업무 연결

업무 상세의 `연결된 업무` 섹션에서 관리한다.

| 버튼 | 동작 |
|---|---|
| `+ 연결 추가` | 연결 종류를 고르고 업무명을 검색해 기존 업무를 연결한다 |
| `+ 연결 업무 만들기` | 새 업무 입력창이 열리고 연결 대상이 채워져 있다. 방향을 고른 뒤 등록한다 |
| 목록의 `×` | 연결을 해제한다 |

연결 종류는 세 가지다.

| 화면 표시 | 뜻 | 프로그램 동작 |
|---|---|---|
| 먼저 할 일 | 이 업무보다 먼저 끝나야 하는 업무 | 미완료면 카드에 자물쇠 아이콘, 진행 시작 시 경고 |
| 다음에 할 일 | 이 업무가 끝나야 할 수 있는 업무 | 상대 업무 쪽에서 "먼저 할 일"로 보인다 |
| 관련 업무 | 참고할 만한 같은 계열 업무 | 양쪽 상세에 서로 표시된다 |

연결 대상이 프로젝트 소속이면 `연결 업무 만들기` 입력창의 메인 일정 칸에 그 프로젝트가 미리 선택된다. 포함하지 않으려면 `없음`을 고른다.

### 같은 프로젝트였는지 판단하는 규칙

- 메인 일정 아래에 있는 하위 일정만 같은 프로젝트로 보고 진행률·지연에 넣는다.
- 먼저 할 일·관련으로만 이어진 업무는 연결 목록에 보여주기만 하고 진행률에는 넣지 않는다.
- 연결의 연결은 따라가지 않는다(1단계만). 사람이 직접 고른 것만 인정한다.

### 템플릿

- 메인 일정 상세의 `템플릿으로 저장`: 현재 하위 일정 구성을 D-day 기준 일수로 저장한다. 담당자는 저장하지 않는다.
- 다른 메인 일정의 `템플릿 불러오기`: 고른 템플릿의 하위 일정을 새 D-day 기준으로 한 번에 만든다. 담당자는 메인 일정의 담당자로 들어간다.
- 설정 탭 `하위 일정 템플릿`에서 목록과 항목을 확인하고, 관리자는 삭제할 수 있다. 이미 만든 하위 일정은 템플릿을 지워도 남는다.

### 삭제

하위 일정이 있는 메인 일정을 삭제하면 두 가지 중 하나를 고른다.

- `하위 일정 N건도 삭제`
- `하위는 남기고 연결만 해제`: 하위 일정은 일반 업무로 남는다.

삭제된 업무를 가리키던 다른 업무의 연결은 자동으로 해제된다.

### 화면별 표시

| 위치 | 표시 |
|---|---|
| 업무 카드(오늘·전체 업무) | 메인: 진행 막대 + `지연 N건`. 하위: 제목 앞 `[메인명]`. 선행 미완료: 자물쇠 |
| 캘린더(월·주) | 하위 일정 제목 앞 `[메인명]`, 메인 일정 막대에 노란 테두리 |
| 날짜별 전체 목록, D-day 목록 | 하위 일정 제목 앞 `[메인명]` |
| 전체 업무 | `프로젝트 필터`: 모든 업무 / 메인 일정만 / 특정 프로젝트(메인 + 하위) |
| iCal 내보내기 | 하위 일정 제목 앞 `[메인명]` |

## 데이터 모델

`lib/types.ts`

```ts
export type TaskLink = {
  id: string;
  taskId: string;                   // 연결 대상 업무 id
  kind: 'prerequisite' | 'related'; // 대상이 먼저 | 관련
  createdBy: string;
  createdAt: string;
  removedAt?: string;               // 해제 시각(해제 기록)
};

export type Task = {
  // ...기존 필드
  parentId?: string;   // 메인 일정 id. 있으면 하위 일정
  offsetDays?: number; // D-day 기준 일수(-40 = 40일 전). 없으면 날짜 직접 지정
  links?: TaskLink[];  // 이 업무에서 건 연결
};

export type ProjectTemplate = {
  id: string;
  name: string;
  items: { title: string; offsetDays: number; categoryId: string; checklist: string[] }[];
  createdBy: string;
  createdAt: string;
};

export type WorkspaceState = {
  // ...기존 필드
  projectTemplates?: ProjectTemplate[];
};
```

### 저장 규칙

- **하위 일정 날짜:** `date`에 실제 날짜를 저장하고, `offsetDays`는 D-day 기준이라는 표시로 함께 둔다. 기존 캘린더·목록·보고서가 `date`만 읽어도 그대로 동작하게 하려는 선택이다.
- **연결 방향:** 연결은 한쪽 업무의 `links`에만 저장한다. "B는 A가 끝나야 함"은 B의 `links`에 `{ taskId: A, kind: 'prerequisite' }`로 저장한다. A 쪽의 "다음에 할 일"은 다른 업무의 `links`를 훑어 계산한다.
- **1단계 구조:** `parentId`는 `parentId`가 없는 업무만 가리킬 수 있다. 하위 일정을 가진 업무는 다른 일정의 하위로 넣을 수 없다.
- **순환 거부:** A가 B를 먼저 할 일로 두고 있으면 B가 A를 먼저 할 일로 두는 연결은 거부한다. 같은 두 업무 사이의 중복 연결, 자기 자신과의 연결도 거부한다.

### 서버 병합

`app/api/state/route.ts`

- `mergeTaskLinks`: 같은 업무를 두 사람이 동시에 저장해도 연결이 사라지지 않도록 `links`를 연결 id 기준 합집합으로 합친다.
- 연결 해제는 배열에서 지우지 않고 `removedAt`을 남긴다. 한쪽이라도 해제했으면 해제 상태를 유지하므로, 합집합 병합 때 해제한 연결이 되살아나지 않는다.
- `projectTemplates`도 다른 배열처럼 id 단위로 병합하고, 삭제는 기존 `deletedIds` 기록을 쓴다.
- 클라이언트 오프라인 복구용 `mergeWorkspaceStates`에도 `projectTemplates`를 추가했다.

| 계산 | 규칙 |

## 검증

2026-09-27, 시드 데이터와 가짜 API를 쓰는 임시 화면에서 Playwright로 확인했다. 운영 데이터는 사용하지 않았고 임시 화면과 테스트는 커밋하지 않았다.

- 메인 생성 → D-40·D-45 하위 추가 → 날짜 자동 계산, `0/2 · 0%`, `지연 2건`
- 관리자 체크 → `1/2 · 50%`, 팀원 체크 → `완료 요청`
- 연결 업무 만들기(먼저 해야 함) → 진행 시작 경고 확인창
- 템플릿 저장 → 다른 메인에서 불러오기 → 새 D-day 기준으로 2건 생성
- 행사일 변경 → 미완료 D-day 기준 하위만 이동, 완료된 하위는 유지
- 프로젝트 필터, 캘린더 `[메인명]` 태그, 설정 탭 템플릿 목록
- 메인 삭제(하위 남김) → 하위의 `parentId` 해제, `deletedIds` 1건
- `next build`, TypeScript, Oxlint 통과, 화면 오류 0건

`tests/e2e/work-calendar.spec.ts`는 로그인이 필요해 이번에는 실행하지 않았다.

## 주의할 점

- 하위 일정은 1단계만 둔다. 더 잘게 나눌 일은 하위 일정의 체크리스트로 쓴다.
- 해제한 연결(`removedAt`)은 배열에 계속 남는다. 양이 적어 문제는 없지만 `deletedIds`처럼 장기적으로 정리 정책이 필요하다.
- 연결 합집합 병합은 `links`에만 적용된다. 같은 업무의 다른 필드는 여전히 마지막 저장이 우선한다.
- 보고서 탭의 프로젝트 진행률 표시는 아직 구현하지 않았다.
- 확인창은 브라우저 기본 `window.confirm`·`window.prompt`를 쓴다. 기존 삭제 확인과 같은 방식이다.
