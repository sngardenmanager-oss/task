# 특이사항 탭 구현 문서

## 목적

현장에서 발견한 문제나 공유 사항을 업무보다 가볍게 기록하고, 댓글로 피드백을 모은 뒤 완료 보관하거나 정식 업무로 전환한다.

## 관련 코드

- 화면과 로컬 UI 상태: `NotesView`
- 등록: `NoteForm`
- 수정: `EditNoteForm` 또는 `NotesView.editNote/saveNote`
- 카드: `NotesView.NoteCard`
- 완료/복원: `toggleNote`
- 댓글: `addComment`
- 업무 전환: `convert`
- 삭제: `deleteNote`
- 전체 내용 보기: `viewingNote` + `ModalShell`
- 타입: `SpecialNote`, `Comment`, `Task`

## 데이터 구조

특이사항은 날짜, 분류, 위치, 본문, 긴급 여부, 작성자와 댓글을 저장한다. 완료 시 `completed=true`, `completedAt`을 기록하며 업무 전환 시 `convertedTaskId`로 생성된 업무를 연결한다.

표시용 label은 다음 규칙으로 자동 생성된다.

```text
특이사항-YYYYMMDD-당일순번3자리
예: 특이사항-20260910-003
```

## 목록 정렬

진행 목록은 다음 순서다.

1. 긴급 항목 우선
2. 발생일 최신순
3. label 순

완료 보관함은 `completedAt`, 값이 없으면 `createdAt` 최신순이다. 보관함은 높이를 제한하고 내부 스크롤을 사용한다.

## 등록과 수정

등록 폼은 발생일, 위치, 분류, 본문, 긴급 여부를 받는다. `commenter`는 등록할 수 없고 팀원과 관리자가 등록할 수 있다.

현재 작업 트리의 수정 UI는 여러 `window.prompt`를 연속 호출하던 방식에서 `EditNoteForm` 모달로 전환되어 있다. 본문 줄바꿈을 유지하며 긴 내용은 카드에서 4줄까지만 보여주고 `전체보기` 모달을 연다.

## 댓글/피드백

- 모든 승인 사용자가 피드백을 작성할 수 있다.
- 댓글은 작성자 id, 본문, ISO 생성 시각을 가진다.
- 관리자는 댓글을 삭제할 수 있다.
- 댓글 사용자에 대해서 서버는 본문·멤버·분류 변경을 막고 기존 댓글 수가 줄어드는 요청도 거절한다.

## 완료 보관함

관리자 체크박스 조작으로 진행/완료 상태를 전환한다.

- 완료: `completed=true`, `completedAt=현재 시각`
- 복원: `completed=false`, `completedAt=undefined`

항목과 댓글 데이터는 삭제하지 않고 같은 배열 안에서 상태만 바꾸므로 감사 이력을 화면에서 계속 확인할 수 있다.

## 정식 업무 전환

`convert(note)`는 특이사항으로부터 `Task`를 만든다.

| Task 필드 | 변환 규칙 |
|---|---|
| title | 본문 앞 40자 |
| description | label, 위치, 전체 본문 결합 |
| date | 특이사항 발생일 |
| categoryId | 특이사항 분류 |
| priority | 긴급이면 urgent, 아니면 normal |
| type | issue |
| sourceNoteId | 원본 특이사항 id |

원본에는 `convertedTaskId`를 저장한다. 이후 버튼은 `업무 전환`이 아니라 `업무 보기`가 되어 중복 생성을 막는다.

## 삭제

관리자가 확인 창을 승인하면 특이사항과 그 안의 댓글을 배열에서 제거하고 id를 `deletedIds`에 추가한다. 서버 병합에서도 해당 id를 제외한다.

## 재사용 방법

이 기능은 이슈 인입함 또는 현장 리포트로 재사용할 수 있다.

```text
QuickNote 입력
  → 우선순위/위치/분류 태깅
  → 피드백 스레드
  → 완료 보관 또는 정식 WorkItem 승격
```

핵심은 `QuickNote`와 `Task`를 처음부터 하나로 만들지 않고, 빠른 기록과 공식 업무를 별도 타입으로 둔 뒤 `sourceNoteId/convertedTaskId`로 양방향 연결하는 것이다.

## 주의할 점

- label의 당일 순번은 현재 클라이언트가 보는 배열 길이로 계산하므로 동시 등록 시 중복될 수 있다. id는 별도 uid라 저장 충돌은 없지만 label을 유일키로 사용하면 안 된다.
- 완료 보관은 삭제가 아니다. 실제 삭제는 관리자 확인과 tombstone을 사용한다.
- 매우 긴 댓글/본문이 많아지면 workspace JSONB payload가 커지므로 장기적으로 comments/notes 테이블 분리가 필요하다.
